# 04 Draw a tile from the Added Space

[Parent specification](../spec.md)

## What to build

Build C: 128 MiB, only to prove that the player loads and draws a tile above `$80000`. A temporary pair of graphics files under `private/` holds synthetic tiles (a pattern, not game art) from tile `$80000`, and appears only in C's descriptor. An option compiled only into C plants one sprite in video memory that points at one of those tiles. The game rewrites sprite memory every frame, so the sprite has to be planted again at a point before each line is drawn, and the tile needs a palette entry that is visible. The capture shows the tile, and the tile differs from tile 0, so tile numbers no longer wrap.

_PT-BR: build C: 128 MiB, só para provar que o player carrega e desenha um tile acima de `$80000`. Um par temporário de arquivos gráficos em `private/` guarda tiles sintéticos (um padrão, não arte do jogo) a partir do tile `$80000`, e aparece só no descritor do C. Uma opção compilada só no C planta um sprite na memória de vídeo apontando para um desses tiles. O jogo reescreve a memória de sprites a cada quadro, então o sprite precisa ser plantado de novo num ponto anterior ao desenho de cada linha, e o tile precisa de uma entrada de paleta visível. A captura mostra o tile, e o tile é diferente do tile 0, então os números de tile não dão mais a volta._

**Suggested model and effort:** Opus 5.5, high. It touches the renderer and video memory, with several traps; failed attempts with a smaller model usually cost more. The final visual check is the owner's. / _Opus 5.5, esforço alto. Mexe no renderizador e na memória de vídeo, com várias armadilhas; tentativas falhas com um modelo menor costumam custar mais. A conferência visual final é do dono._

## Result (2026-11-16, Windows)

**Closed: a tile of the Added Space is loaded, decoded and drawn.** Commands are in `tools/kof2003/growth/README.md`.

- Build C is made by `growth/added_space_patch.py apply`, which changes three things in the private copies and can undo all three: the graphics size to 128 MiB, the synthetic pair as the **fifth** pair of the descriptor, and one call in the renderer's `video_render_line()`, guarded by `#ifdef KOF2003_ADDED_SPACE_PROOF`. The CMake option of the same name, off by default, compiles `growth/added_space_proof.c` into the player and defines the macro. Builds A and B pass neither, so they carry neither.
- The pair is 1,024 bytes a file, 16 synthetic tiles of a made-up diagonal pattern (`growth/added_space_tiles.py`), written to `private/work/graphics-growth/synthetic/` and reached through `rom-c/`, a folder of hard links to the real ROM folder plus the pair. The four original pairs fill exactly 64 MiB, so the first synthetic tile is tile number `$80000`.
- Where and how the sprite is planted: in the renderer, at the top of `video_render_line()`, before `draw_sprites()` — so it is planted again before every one of the 224 visible lines of every frame. It is sprite 380 (the last one), tile list word `$5F00`, with the tile number's bits 16-19 in attribute bits 4-7 (attribute `$0180`: palette 1, tile `$80000`, no auto-animation, no flip), no shrink, one tile tall, at screen (152, 96). The fifteen pens of palette 1 are written with it, every line.
- Reversibility, on the real private files: descriptor SHA-256 `a20ef4a7…ab6a3` before, `ea2cdb5b…b8df` with the patch, `a20ef4a7…ab6a3` after undo; renderer `d81ee030…c766` before, `00a77fea…6217` with the patch, `d81ee030…c766` after undo. Both originals are back byte for byte, which is also why ticket 02's "B equals A" still holds: nothing in A's or B's definition changed, and `build-b` was never rebuilt.
- B still equals A: `match.compare_builds` was run again after all of this, with the whole apply-and-undo cycle behind it, and gave `coin-start` 5 of 5 and `team-match` 7 of 7 captures identical, 0 mismatches in both builds, and the same hashes as the table of ticket 01. B's memory was 419 MiB peak working set and 298-300 MiB steady, as in 02.
- Captures, `coin-start`, frames 2,000, 3,000 and 4,000 (attract mode and team selection). Every one: all 256 pixels of the 16x16 box at (152, 96) are exactly the colours tile `$80000` must show; build B at the same frames shows no such tile. Candidate SHA-256 `2a8b53b6…be5d`, `21f704cd…890d`, `632c5d2b…164b`; reference `b6cb2c44…f9b2`, `6e5147fd…ffb2`, `a5e82aba…1675`. `--verify`: 0 mismatches in both builds, and the run was repeated with every capture coming out byte-identical the second time. Blocks checked: C 1,934,206 and B 1,934,204 in the first run, C 1,934,242 and B 1,934,215 in the second, i.e. the two builds sit inside the few dozen blocks of run-to-run jitter ticket 01 recorded, so nothing in the planting changes what the CPU runs.
- The tile is not tile 0: synthetic tile `$80000` SHA-256 `0243f325…8441`, Graphics Set tile 0 `38723a2e…d5ca`. Tile numbers no longer wrap from `$80000` to `$00000`.
- **Traps found**, for the Rehearsal:
  1. *Sprite memory is rewritten every frame.* One write at start-up draws nothing; the sprite has to be planted again before each line, which is why the call sits in `video_render_line()` and not in the loading code.
  2. *The palette is not ours.* A tile drawn with pens the game left black is invisible, so the fifteen pens are written again with the sprite.
  3. *The sprite chain.* A sprite with the sticky bit continues the previous one, so planting into a chained slot moves someone else's sprite. Sprite 380 is the last one: nothing can chain onto it, and its own sticky bit is cleared.
  4. *The BIOS tests video memory and palette RAM while the board boots*, writing a pattern and reading it back. Planting during that test left the game on a blank screen of two colours for the whole run, with about half the blocks per frame of a healthy build — it never got past the test. The planter therefore leaves the board alone until frame 1,000 (`PROOF_FIRST_FRAME`), and `run_added_space.py` refuses to look for the tile at or before that frame. **This is the trap that cost the most here; real tiles in the Added Space will be written by the game itself, but any later test code that writes video memory from outside the game has to wait for the boot to finish.**
  5. *Not hit, but real:* the LSPC draws at most 96 sprites per line, counted from sprite 0, so on a line that already holds 96 the planted sprite 380 is skipped. It did not happen at these frames.
  6. *Not hit, but real:* the fixed layer is drawn after the sprites, so a tile under a non-transparent fix tile would be hidden. (152, 96) is clear at these frames.
- Checked by 50 new tests (`growth/tests/test_added_space_tiles.py`, `test_added_space_patch.py`, `test_verify_added_space.py`, `test_run_added_space.py`), all with made-up data: the tile encoding against the renderer's decoding rule, the palette formula on both sides, the patch's idempotence and reversibility including CRLF, the capture reader row filter by row filter, and the C-against-B run with a fake player, including what makes such a run fail. 91 tests pass in `growth`, `match` and `loader` together, and ticket 03's loader test still passes against the restored toolkit. `growth/verify_added_space.py` reads the proof's constants out of the C file, so neither the expected position nor which tile is expected can drift from what is planted.
- Two refusals worth knowing about, both from the review: `added_space_patch.py` refuses a descriptor that does not list exactly four pairs, because the Added Space starts at the fifth pair and a fifth pair added to a descriptor with three would not begin at tile `$80000`; and `prepare_rom_dir` refuses to build the ROM folder for C on top of the folder it links from, because it deletes whatever does not belong in it and that folder holds the owner's dumps.
- Native code: after the whole apply-and-undo cycle the 26 files in `generated/` are byte-identical to the hashes recorded in ticket 02, and the rebuilt 64 MiB player runs the `coin-start` script with 0 uncovered entry points.
- Owner check (2026-11-16): the owner looked at the captures and found the square. He then asked whether build B has one too, because at frame 2,000 the tile lands on the title logo, where B happens to have white and orange art in those same 16 pixels. Settled by comparing the pair pixel by pixel: exactly 256 pixels differ between C and B, and they are exactly the box at x 152-167, y 96-111, so the two builds draw the same game and differ only by the planted tile; in B not one of the 256 matches the tile's colours. **For the Rehearsal: plant test graphics where the game leaves the screen clear, not over the title logo, and compare the pair rather than looking at one capture alone.** `private/work/graphics-growth/conferir-04.py`, outside git, reprints the per-capture verdict on demand.
- Left as it was: the descriptor is back at 64 MiB, the CMake option is off, and the player in `mvs-native-build` was rebuilt from the restored descriptor. `build-a` and `build-b` were not touched. Build C's executable is kept in `private/work/graphics-growth/build-c/`.
